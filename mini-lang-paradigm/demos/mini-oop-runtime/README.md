## Overview

This module implements a minimal but complete Object-Oriented Programming runtime in C99. Unlike C++ where vtables are generated by the compiler, we explicitly manage class metadata, method tables, and object instances.

### Core data structures:

```
Class {
  name, vtable[], vtable_size,
  parent_class, instance_size,
  num_fields, field_names[]
}

Object {
  class*, fields[]
}

Method {
  name, arity, fn_ptr
}
```

## Vtable Dispatch

### What is a vtable?

A **virtual method table** (vtable) is an array of function pointers associated with each class. When a method is called on an object, the runtime looks up the correct function through the class's vtable.

### How dispatch works:

1. `object_call_virtual(obj, "method_name", args)` is called
2. The runtime searches `obj->class->vtable` for a method named `"method_name"`
3. If found, the function pointer at that index is invoked with `(obj, args)`
4. If not found in the current class, the runtime walks up `parent_class` chain

### Dispatch algorithm:

```
method_index = class_method_index(obj->class, name)
  → walk from current class up to root
  → return first index where vtable[i].name == name

dispatch: obj->class->vtable[method_index](obj, args)
```

### Vtable layout convention:

- Methods are stored by index (positional)
- Overrides preserve the index of the parent's method
- New methods are appended at the end
- The vtable always has exactly `vtable_size` entries

## Single Inheritance

### Class hierarchy construction:

```c
Class* animal = class_create("Animal", sizeof(Object));
class_add_method(animal, "speak", 0, animal_speak);

Class* dog = class_inherit("Dog", animal);
// dog.vtable is a copy of animal.vtable
class_override_method(dog, "speak", dog_speak);
// replaces vtable[i].fn_ptr for "speak"
```

### Inheritance rules:

1. Subclass copies parent's entire vtable
2. `class_inherit()` performs a shallow copy of methods and field names
3. Overrides modify the entry *in place* — no new entry is created
4. The parent pointer enables walking the hierarchy for method lookup

### Runtime behavior:

```
Object* d = object_create(dog);
object_call_virtual(d, "speak", NULL);
// Finds "speak" at index 0 → calls dog_speak
```

If you call through a base pointer:

```c
Object* a = (Object*)d;  // upcast
object_call_virtual(a, "speak", NULL);
// a->class == &Dog → still dispatches to dog_speak
```

This is **polymorphism** via vtable indirection.

## Multiple Inheritance

### The Diamond Problem

Multiple inheritance introduces the **diamond problem**: if D inherits from B and C, which both inherit from A, does D get one copy of A's data or two?

### Implementation approaches:

#### 1. Repeated inheritance (non-virtual base)
- D contains two copies of A's fields
- Ambiguity resolved by explicit qualification
- Simpler memory layout

#### 2. Virtual inheritance (shared base)
- D contains exactly one copy of A's fields
- Requires offset adjustments in vtables
- More complex but semantically correct

### Vtable thunks

With multiple inheritance, pointer adjustment is needed:

```
struct MIObject {
    Class* class;        // primary vptr
    Class* secondary;    // for second base
    ptrdiff_t offsets[]; // this-adjustment thunks
};
```

When calling a method from a secondary base, the `this` pointer must be adjusted:

```
void* mi_call(MIObject* obj, int base_idx, const char* method, void** args) {
    void* adjusted_this = (char*)obj + obj->offsets[base_idx];
    return obj->class->vtable[method](adjusted_this, args);
}
```

## Mixins

### Concept

A **mixin** is a class that provides functionality to be inherited by subclasses, but is not meant to be instantiated on its own. Mixins enable code reuse without the complexity of full multiple inheritance.

### Implementation:

```c
// Linearize mixins into the class
Class* class_with_mixins(const char* name, Class** mixins, int mixin_count) {
    Class* cls = class_create(name, sizeof(Object));
    for (int i = 0; i < mixin_count; i++) {
        // Copy all methods from mixin
        for (int j = 0; j < mixins[i]->vtable_size; j++) {
            if (class_method_index(cls, mixins[i]->vtable[j].name) < 0) {
                class_add_method(cls,
                    mixins[i]->vtable[j].name,
                    mixins[i]->vtable[j].arity,
                    mixins[i]->vtable[j].fn_ptr);
            }
        }
    }
    return cls;
}
```

### Mixin composition rules:

1. **First-come-first-served**: if two mixins define the same method, the first wins
2. **Linearization**: mixins are resolved in order (like Python's MRO)
3. **No diamond**: mixins should be independent (no shared base)
4. **State via fields**: each mixin reserves its own field slots

### Example: LoggingMixin + SerializableMixin

```c
Class* logger = class_create("LoggingMixin", sizeof(Object));
class_add_method(logger, "log", 1, log_impl);

Class* serial = class_create("SerializableMixin", sizeof(Object));
class_add_method(serial, "serialize", 0, serialize_impl);

Class* mixins[] = { logger, serial };
Class* model = class_with_mixins("UserModel", mixins, 2);
// model now has "log" and "serialize" methods
```

## Interfaces / Abstract Classes

### Abstract classes

An abstract class defines a contract (method signatures) without implementations:

```c
typedef struct {
    char   name[OOP_MAX_NAME_LEN];
    Method signatures[OOP_MAX_METHODS];
    int    sig_count;
} Interface;
```

### Interface conformance check:

```c
bool class_implements(Class* cls, Interface* iface) {
    for (int i = 0; i < iface->sig_count; i++) {
        if (class_method_index(cls, iface->signatures[i].name) < 0) {
            return false;  // method not found
        }
    }
    return true;
}
```

### Pure virtual methods:

Mark a vtable entry with `fn_ptr == NULL`:

```c
void class_add_abstract_method(Class* cls, const char* name, int arity) {
    Method m = { .name = name, .arity = arity, .fn_ptr = NULL };
    cls->vtable[cls->vtable_size++] = m;
}
```

When dispatch encounters a NULL fn_ptr, it triggers a runtime error.

## Multiple Dispatch

### Single dispatch (what we have)

In single dispatch, the method called depends only on the **receiver's** type:

```
obj.method(arg1, arg2)  →  dispatched on obj's type only
```

### Double dispatch / Multiple dispatch

In multiple dispatch, the method depends on the types of **all arguments**:

```
method(obj1, obj2, obj3)  →  dispatched on types of all three
```

### Implementation: dispatch matrix

```c
typedef void* (*MultiMethod)(void*, void*, void*);

// 2D dispatch table: [type_of_arg0][type_of_arg1] → fn
void* dispatch2(Object* a, Object* b, MultiMethod** table) {
    int ta = class_id(a->class);
    int tb = class_id(b->class);
    return table[ta][tb](a, b);
}
```

### Visitor pattern as double dispatch:

```c
void* accept_visitor(Object* obj, Object* visitor) {
    return object_call_virtual(visitor, "visit", (void*[]){ obj });
}
// Inside visitor.visit(concrete_obj):
//   dispatch is determined by BOTH visitor type AND obj type
```

### Generalization to N-ary dispatch:

A general multi-method system maps N-tuples of class IDs to implementations:

```c
typedef struct {
    int    arity;
    void** fun_matrix;  // N-dimensional array of function pointers
    int*   dimensions;  // size of each dimension
} GenericFunction;

void* gf_call(GenericFunction* gf, Object** args) {
    int index = 0;
    int stride = 1;
    for (int i = 0; i < gf->arity; i++) {
        int cid = class_id(args[i]->class);
        index += cid * stride;
        stride *= gf->dimensions[i];
    }
    MultiMethod fn = gf->fun_matrix[index];
    return fn(args);
}
```

## Memory Model

### Object layout in memory:

```
+------------------+
| class*           |  8 bytes (pointer)
+------------------+
| fields[0]        |  8 bytes
| fields[1]        |  8 bytes
| ...              |
| fields[N-1]      |  8 bytes
+------------------+
```

### Class layout in memory:

```
+------------------+
| name[64]         |  64 bytes
+------------------+
| vtable[0]        |  24 bytes each (name + arity + fn_ptr)
| vtable[1]        |
| ...              |
+------------------+
| vtable_size      |  4 bytes
+------------------+
| parent_class*    |  8 bytes
+------------------+
| instance_size    |  8 bytes
+------------------+
| field metadata   |  variable
+------------------+
```

### Allocation strategy:

- `malloc` for each Class and Object
- No garbage collection — manual memory management
- vtable is stored inline in the Class struct (no separate allocation)

## Comparison with C++/Java vtables

| Feature              | Our Implementation    | C++                     | Java                    |
|---------------------|----------------------|------------------------|--------------------------|
| Vtable location     | Inline in Class      | Separate, compiler-gen  | In Class object (JVM)   |
| Method lookup       | Name-based linear    | Index-based (compile)   | Name-based (JIT opt)    |
| Multiple inheritance| Not supported        | Yes (complex layout)    | No (interfaces only)    |
| Virtual by default  | All methods virtual  | opt-in (virtual kw)     | All methods virtual     |
| RTTI                | class ptr only       | typeid + vtable         | instanceof + Class      |
| Thunks              | N/A                  | this-adjustment thunks  | Interface method tables |

## Performance Considerations

1. **Method lookup**: Our name-based lookup is O(n) per call. Production vtable implementations use O(1) index-based dispatch.
2. **Cache locality**: Inline vtables in Class struct improve cache behavior
3. **Memory overhead**: Each Object has a class pointer (8 bytes) overhead
4. **Inline caching**: Could be added by caching last-used method index per call site
5. **Monomorphization**: For known types, dispatch could be devirtualized at compile time

## Extensions & Future Work

- **Properties**: getter/setter methods with special dispatch rules
- **Introspection**: runtime type information beyond class name
- **Method missing**: `doesNotUnderstand:` style message forwarding
- **Mixins with state**: merge field layouts from multiple mixins
- **Prototype-based OOP**: like JavaScript — clone objects instead of instantiate classes
- **Trait composition**: like Rust traits or Scala traits with conflict resolution
- **Meta-object protocol**: make the OOP system itself programmable
